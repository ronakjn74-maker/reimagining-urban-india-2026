1. **BLOCKER — §11.3 (SbcDesign path), §23 item 2, §25 Q-A7** — The office's *usual* path (SbcDesign, forces only) never names which ETABS tables carry the forces. Appendix B §2 lists only MODEL and DESIGN tables; no ANALYSIS RESULTS table appears anywhere in the plan or the appendix. The path is therefore not specified end-to-end: nothing says which table, which columns, which units, or what row shape (one row per combo per station, with Max/Min "Step Type" rows for RS/envelope cases) the Phase 2.5 import must deliver to `ColumnDesign`.
   **Fix (append to §11.3, before the table):**
   > **Force tables consumed on the SbcDesign path** (ANALYSIS RESULTS branch of Show Tables; header spellings "(verify)" until the owner's ETABS 22 export is in `inputs\`):
   > - `Element Forces - Columns` — `Story` | `Column` (=Label) | `Unique Name` | `Output Case` | `Case Type` | `Step Type` (Max/Min/blank) | `Station` | `P` | `V2` | `V3` | `T` | `M2` | `M3`. One row per column per combo per station; `P` compression negative in ETABS sign convention — the adapter flips to SBC's convention and records the flip in Provenance.
   > - `Pier Forces` — `Story` | `Pier` | `Output Case` | `Case Type` | `Step Type` | `Location` (Top/Bottom) | `P` | `V2` | `V3` | `T` | `M2` | `M3`. Forces are for the whole pier (all legs), in pier local axes (axis angle from `Pier Section Properties`).
   > - `Load Combinations` (+ `Load Combination Definitions`) — combo name, type (Linear Add / Envelope / Abs Add), case list and factors → used to classify ULS vs SLS combos (§11.3a).
   > - `Story Drifts`, `Joint Reactions` — read by Phase 2.5 for other purposes; not needed by the Detailer.
   > Missing `Element Forces - Columns` or `Pier Forces` → `STATUS: INCOMPLETE` for the run (G1). A column present in `Frame Assignments - Summary` with `Design Type = Column` but absent from the force table → INCOMPLETE for that member with ACTION "export was Selection Only or analysis not run".
   Also add to Q-A7 the request: "…and the forces tables (`Element Forces - Columns`, `Pier Forces`, `Load Combinations`, `Story Drifts`, `Joint Reactions`) and the `Program Control` table from the same run".

2. **BLOCKER — §11.3 row `Pu/Mu` and §13 `ColumnStation`** — The plan passes only an "Envelope" of Pu/Mu to the design and to the record. Biaxial column design (IS 456 39.6) and the IS 13920 capacity-shear check must be done **per combination** (P and M2/M3 of the *same* combo at the *same* station); an envelope that pairs max P with max M2 and max M3 from different combos is neither safe nor economical and cannot reproduce ETABS's `PMM Combo`. Which combos are design combos (ULS only; exclude SLS / drift combos; how Envelope-type combos and Max/Min step rows are expanded) is nowhere decided.
   **Fix (new §11.3a "Design combinations and envelopes"):**
   > The Phase 2.5 import hands `ColumnDesign` / wall design the **full per-combo, per-station force set** (`ForceStation(Story, Label, UniqueName, Combo, StepType, Location_mm, P, V2, V3, M2, M3)`), never a pre-enveloped Pu/Mu. Design combos = every `Load Combination` whose name matches the project's ULS filter (default regex `^(U|ULS|DCon|COMB)` and `Case Type = Combination`, setting `[Detailer] UlsComboRegex`), expanded so that an Envelope-type combo contributes its Max and Min rows as two load sets. SLS/drift combos are excluded. The design routine iterates every (combo, station), checks biaxial PMM per combo, and reports the **governing combo name** in `ColumnStation.PmmCombo` / `VMajorCombo` / `VMinorCombo`; `Pu_kN, Mu2_kNm, Mu3_kNm` on the record are the values *of that governing combo*, not component-wise maxima. `ColumnDesignRecord.Envelope` is the station with the largest `AsRequired_mm2` (and separately the max `Avs*`), tagged with its combo. Wall stress trigger (IS 13920 10.4.1) likewise runs per combo on `Pier Forces` and reports the governing one. If zero combos pass the ULS filter → `STATUS: INCOMPLETE "no ULS combination recognised — set UlsComboRegex"`.
   And in §13 add `double? Vu2_kN, double? Vu3_kN` to `ColumnStation` (Appendix B §5 has `vuMajor_kN/vuMinor_kN`; the plan dropped them, but the lap tension check F-10 and the capacity-shear comparison need them).

3. **MAJOR — §11.2, §13 `WallPierDesignRecord.Legs` (≥1 mandatory), §15.2 step 2** — `Pier Section Properties` gives only `Width/Thick Bot/Top`, axis angle and CG per story (App. B §2.1); it does **not** give per-leg end coordinates. Per-leg `x1,y1,x2,y2` exist only in the "(verify)" `Shear Wall Pier Design Details` table (EtabsDesign path only) and never on the forces-only path. So `Legs` cannot be filled as specified for multi-leg piers, which L2 matching and the whole wall workflow depend on.
   **Fix (replace the `Pier Section Properties` bullet in §11.2 step 3 and add to §11.3):**
   > `PierLegs` are **derived** by the importer, on both paths: `Area Assignments - Pier Labels` (Story, Label, Unique Name, Pier Name) → the set of wall area objects per (Story, Pier); `Area Object Connectivity` + `Point Object Connectivity` → each object's corner points; project to plan, take the two long edges, collapse to a centreline segment with thickness from `Area Section Properties`/`Wall Property Definitions`; merge collinear segments sharing an endpoint (tolerance 25 mm) into one leg; number legs by the order ETABS reports them (longest first = pier local axis, release note 11414). `Pier Section Properties` is used only to cross-check `Width Bot ≈ Σ leg lengths` (±5 %) and to take `AxisAngle_deg`, `CgBot/CgTop`, `Ag_mm2`. When `Shear Wall Pier Design Details` is present its leg coordinates override the derived ones and a mismatch > 25 mm is a WARNING. A pier whose area objects cannot be reduced to straight legs (curved or meshed walls with openings) → `INCOMPLETE "pier legs not derivable"`.

4. **MAJOR — §11.3, §15.1 (SbcDesign walls)** — `Pier Forces` are for the composite pier, but the plan has the SBC wall design produce `PierShear` per leg and BE flags per leg/edge. Nothing says how a whole-pier force set is turned into per-leg design for L/C/T cores on the SbcDesign path (which is the usual path).
   **Fix (append to §15.1 SbcDesign bullet):**
   > On the SbcDesign path a **single-leg** pier is designed as a rectangular wall from `Pier Forces` directly. A **multi-leg** pier is designed as one composite section (legs unioned, axis per `Pier Section Properties`) for flexure/axial and the stress trigger; shear per leg is taken as `V2`/`V3` apportioned by leg stiffness (`t·l³` about the relevant axis) — the apportioning rule is printed in EXPLAIN and the pier is set to REVIEW (never READY) until the owner confirms the rule (new Q-B11). If the SBC wall design cannot handle the composite shape in V1, the record is produced with `Status = NotDesigned` and the pier is `INCOMPLETE "multi-leg pier needs ETABS design (set DesignSource=EtabsDesign for walls) or manual input"`.

5. **MAJOR — §11.3 `Key` row, §12 L1, §13 `MemberKey`** — On the SbcDesign path the plan says "SBC mark + storey directly (no label mapping needed)". But the forces arrive keyed by ETABS (`Story`, `Label`/`Pier`, `Unique Name`), not by SBC mark; the mapping *is* needed and lives in `LabelMap` written at .e2k export. The .e2k cannot carry Unique Names (ETABS assigns them at import, App. B §1b), so LabelMap maps mark → (Story, Label [, plan X/Y]) only, and ETABS labels are renumbered whenever the owner deletes an object (App. B §4). A stale LabelMap silently maps a mark to the wrong column.
   **Fix (replace the `Key` row in §11.3 and add a paragraph):**
   > `Key` — `(Story, Label)` from the force table, joined to the SBC mark through `LabelMap` (mark → Story, Label, X, Y, B, D written at .e2k export). The join is **verified** by geometry: `Point Object Connectivity` X/Y of the column's I-point must be within 100 mm of the LabelMap X/Y and the `Design Section` B×D within 10 %; otherwise the row is `MATCH FAILED "label C14 no longer at (12450, 6500) — ETABS labels renumbered; re-export the .e2k or accept by geometry"`. On the first successful import the `Unique Name` (and `GUID` from the connectivity table) is written back into LabelMap and preferred on every later import. **Recommended .e2k convention:** SBC writes the ETABS *pier label* equal to the SBC wall mark (`PIER "SW2"`), and writes the column Unique Name equal to the SBC mark where the e2k version supports it (verify in E2kWriter), so that on a fresh ETABS import no label mapping is needed for walls.

6. **MAJOR — §12 L0 Storey, §13 `MemberKey.Tower`** — The normaliser `"3F" / "Story3" / "STOREY 3" → 3` strips tower prefixes (`T1-Story4`, App. B §4 pitfall 13) and will merge towers; `Tower` is on `MemberKey` but `StoreyMapper` ignores it. Also ETABS exports "Base" as a story and SBC storeys may not.
   **Fix (append to L0 row):**
   > Story names are matched on the **full string** first; the numeric normaliser runs only on the part after the last `-` when `Story Definitions` has a `Tower` column, and the tower token must equal `Project.EtabsTower` (setting; default = the only tower). Two ETABS stories normalising to the same SBC storey → `MATCH FAILED (storey ambiguous)` for that storey, never first-wins. `Base` is mapped to the foundation level and produces no members.

7. **MAJOR — §11.2 step 2 and §13 units** — Units handling is incomplete in three ways that the owner's "kN, mm" export procedure (Q-A7, App. B §6) triggers directly: (a) with length = mm, ETABS moments export as **kN·mm**, not kN·m, so the contract's `Mu2_kNm` needs a ×10⁻³ conversion; (b) units are **per column** in the units row (a table mixes mm, mm², mm²/m, kN, kN-mm, MPa, deg, unitless), not per table; (c) `Rebar Area` may appear as `mm²` even in kN-m exports, and `Av/s` as `mm²/m` or `mm²/mm` depending on version.
   **Fix (replace step 2):**
   > `UnitsRowParser` reads the units row **per column**, maps each header to a contract quantity (force, length, area, area/length, moment, stress, angle, ratio) and converts with a fixed table (`kN-mm→kN·m ×0.001`, `N→kN`, `m→mm`, `m²→mm²`, `mm²/mm→mm²/m ×1000`, `N/mm²=MPa`, `kgf`/`tonf`/`lb` refused). An unknown unit string, a blank units cell on a numeric column, or a units row absent (CSV channel) → `STATUS: INCOMPLETE "units unknown for column <Rebar Area> in <table>"`; never defaulted. `Provenance.SourceUnits` records the force/length pair from `Program Control` (`CurrUnits`, verify) and the per-column strings are kept in the import log.

8. **MAJOR — §11.2 step 2 "Numbers parsed with InvariantCulture; mixed separators fail loudly"** — In an .xlsx the numeric cells are culture-free (OpenXML stores doubles), so the rule is moot there; in a CSV/text export from a decimal-comma Windows locale, InvariantCulture parsing of `"1,260"` gives 1260 (or splits the field when the delimiter is also a comma) — a silent 1000× error, not a loud failure. The plan's "mixed separators" test does not catch a file that is *uniformly* decimal-comma.
   **Fix (append to step 2):**
   > Culture: for .xlsx, numeric cells are read as doubles; a numeric column whose cells are *strings* is parsed only if every value matches `^-?\d+(\.\d+)?([eE][-+]?\d+)?$`, else `INCOMPLETE "text numbers in <column> — re-export with English (US) number format"`. For CSV/text: the delimiter is detected from the header row (tab preferred; comma accepted only when no cell contains a comma-decimal pattern `\d,\d`); any `\d,\d` in a numeric column → refuse the file with the same ACTION. The import log prints the detected delimiter and culture decision.

9. **MAJOR — §11.2 step 3 / §17 G1** — "Selection Only" exports, design results invalidated by re-analysis, and columns with design procedure "None" (App. B §1a, §4 pitfall 7) all produce *silently partial* design tables. The plan catches a missing row only when a member is picked (§18 example), not at G1.
   **Fix (append to G1 row "Checks"):**
   > completeness: count of rows with `Design Type = Column` and `Design Procedure = Concrete Frame` in `Frame Assignments - Summary` must equal the distinct (Story, Unique Name) in `Concrete Column Design Summary`; same for piers between `Area Assignments - Pier Labels` and `Shear Wall Pier Design Summary`. A shortfall → G1 **Warn** for the run with the list of missing members, each member `INCOMPLETE "no design row — export was Selection Only, design not run after last analysis, or design procedure None"`; a shortfall > 50 % → run blocked (the export is almost certainly partial).

10. **MAJOR — §11.2 step 5, §13 `Provenance`, §16 item 7** — Provenance says `ModelFile`, `ToolVersion` (= etabsVersion) and `ExportDate` are read "per App. B §5", but the plan's required-table list does not include `Program Control` (the only table that carries program version and units; whether it carries the model/file name is "(verify)"), and `ExportDate` has no stated origin. Re-import behaviour is keyed on `FileSha256` of the whole file, so a re-saved identical export (different sha) would mark every member stale.
   **Fix (replace step 5):**
   > Provenance: `ToolVersion` and `SourceUnits` from `Program Control` (`ProgramName`, `Version`, `CurrUnits` — headers verify; table mandatory → missing = INCOMPLETE); `ModelFile` from `Program Control`'s `ModelName`/file column if present (verify), else the import prompts for a revision tag (`Tower-A_R3`) which is stored instead; `ExportDate` = the .xlsx `dcterms:modified` core property, fallback file mtime, always shown to the user at load. `FileSha256` = sha256 of the file **and** `ContentSha256` = sha256 of the canonicalised rows of the tables used (sorted, trimmed, numbers normalised). Staleness per member is decided by the member's `DesignHash` (§16.7), not by the file hash; a new file whose `ContentSha256` equals the previous one is reported "re-import: no change" and nothing is rewritten.

11. **MAJOR — §12 "Persistence and re-match" (b)** — When the import hash changes, entries are "re-validated UniqueName/GUID → label → geometry". With ETABS label renumbering, a column deleted in ETABS makes its label jump to a neighbour; if the stored `UniqueName` is gone and the fallback goes to *label*, the plan re-matches the mark to the **wrong** column at MATCH level (label equality) with only a section check at G3. Deleted members in ETABS are not handled explicitly at all.
   **Fix (replace (b)):**
   > (b) if the import content hash changed: for each entry, look up the stored `UniqueName` (then `GUID`). Found → re-verify centroid ≤ 100 mm and section ≤ 10 %; pass = match kept, fail = `DATA CONFLICT (member moved/resized in ETABS)`. **Not found** → the member was deleted or the export is partial: the entry is set `MATCH FAILED "UniqueName 147 absent from export — deleted in ETABS or Selection Only"`, and the detail block gets the HOLD tag (§16.7). Label equality is **never** used to re-match an entry that previously had a UniqueName; it may only propose a candidate in the report ("label C14 now at UniqueName 212, 0 mm away — run SBCDETAILMATCH to accept"). A CAD entity whose handle no longer exists → entry removed and reported "C12 @ 3F: CAD member deleted — detail block orphaned (HOLD)".

12. **MAJOR — §13 `Provenance` on the SbcDesign path, §11.3 last row** — `Provenance.Source = SbcDesign, hash of the design run` does not chain back to the ETABS forces file. When the owner re-runs ETABS and re-imports forces but nobody re-runs the SBC design, the details stay "current" because the design-run hash has not changed.
   **Fix (replace the `Provenance.Source` row in §11.3):**
   > `Provenance`: `Source = SbcDesign`; `ToolVersion` = plugin/Calculator version; `FileSha256` = sha256 of the ETABS **forces** export the design consumed (from the Phase 2.5 import record); `Channel = "SbcDesign/ColumnDesign"` or `"SbcDesign/Calculator"`; `TablesUsed` = the force tables of finding 1; `ExportDate` = ETABS export date; plus a new field `string? DesignRunId` (hash of design inputs + settings + code version). G1 compares `FileSha256` of the design run with the *latest* Phase 2.5 import in the drawing: different → every member `INCOMPLETE "design run older than the current ETABS import — re-run SBC design"`.

13. **MAJOR — §11.2 step 3 (sections) and Q-B2** — For L/T/C columns the `SdPolygons` come "from the .e2k", but the EtabsDesign path explicitly allows a hand-built ETABS model (step 4: `SbcMark = null`) where no SBC .e2k exists, and the Excel export does not include SD polygons unless the "(verify)" v20+ "SD Section Data" tables are ticked.
   **Fix (append to step 3):**
   > SD sections: polygons and drawn bars are read from `Frame Section Property Definitions - Section Designer` / "SD Section Data" tables when present (headers verify); else from the model's .e2k (`$ SECTION DESIGNER SECTIONS`) if the user supplies it beside the .xlsx; else every column on an SD section is `INCOMPLETE "SD section <name>: polygon not in export — tick the SD tables or supply the .e2k"`. Add "SD Section Data (if any SD section exists)" and "Program Control" to the ~12 fixed tables in the export procedure (Q-A7).

14. **MAJOR — §12 L1/L3 verification and §17 G3** — L1 says "geometry still verified at L3", but G3 (the only verification gate) checks section, rotation and storey height, not centroid position. A LabelMap/label match to a column at the wrong plan position with the same section passes every gate.
   **Fix (append to G3 "Checks"):**

Applies to every match level including L1 and the SbcDesign path (using LabelMap X/Y when ETABS connectivity tables are absent).

16. **MINOR — §11.2 step 3 `Frame Sections`** — `t3`/`t2` to `B_mm`/`D_mm` orientation is not stated; with `Angle` from `Local Axes` it decides whether a 300×600 is matched to the CAD 300×600 or 600×300 (G3 fails at 100 %).
